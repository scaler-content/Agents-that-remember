3.0

Why agents need memory

In Section 2 your agent learned to reason and act with tools. But a tool-using agent that can't remember earlier conversations, your preferences or what it did last time still starts every chat from zero.

Without memory, every interaction feels transactional. With memory, an agent can recall what you asked a minute ago, keep important facts across sessions, adapt to your preferences, and stay on track in long-running work. Memory is what turns a reactive assistant into a dependable collaborator.

This is the natural next step after tools: tools let an agent act; memory lets it learn from history and keep context. Together they're the foundation of agents that feel coherent, useful and increasingly personal.

✦Think of it like this

Your neighbourhood kirana uncle versus a vending machine. The vending machine serves everyone the same way, every time. The kirana uncle remembers you buy toned milk, asks if your mother's knee is better, and keeps your usual brand aside. Same transaction, completely different experience. Memory is the difference.

3.1

What is agent memory?

is an agent's ability to keep past information so it can maintain context and make better decisions.

Picture a chat with a travel agent. You ask, "What are good places to visit in Bangalore?" It replies, "Lalbagh Botanical Garden is a favourite." You follow up: "What's the best time to visit it?" The agent knows "it" means Lalbagh and answers, "Early morning, and during the Republic Day or Independence Day flower shows." That small "it" only works because the agent remembered the previous turn.

    Why memory matters

    1. 1

      Contextual intelligence

      Not just storing data, but understanding the why and how behind a request. By spotting patterns in how you work, the agent answers in a way that fits your situation and sees the bigger picture of your project instead of treating each prompt as isolated.

    2. 2

      User preferences

      The agent builds a profile of how you like to work: a professional tone, a certain format, constraints you mentioned before. You don't have to repeat "always keep it under 100 words" in every new chat.

    3. 3

      Knowledge retention

      Persistent memory that grows over time. Instead of staying static, the agent becomes a better problem-solver the more you use it, remembering complex problems you solved together and using them next time.

    3.2

    Types of agent memory

    Memory isn't one thing. An agent needs a scratchpad for the conversation in front of it, and a longer-lasting store for what it should still know next week.

    Language models on their own are largely : they only know the current prompt and whatever fits in their . Agents need ways to keep and use information over time. A helpful way to think about this comes from cognitive architectures such as , which organise an agent around reasoning, action and memory. The key idea for us: an agent may need short-term memory for the current interaction, long-term memory for stable knowledge across sessions, and episodic memory to recall past experiences.

    Short-term memory, or working memory

    This is the agent's scratchpad: whatever it's focusing on right now. It's why a chatbot can feel like a natural conversation partner. Instead of treating each message as brand new, it keeps track of the current session, so its answers follow what's already been said. Without it, the agent would forget your question the moment you asked a follow-up.

    Technically it's handled by the context window or a : a fixed amount of space. As the conversation grows, the oldest information is pushed out to make room for the new.

    The catch: short-term memory keeps one interaction smooth but saves nothing once the session ends. On its own, it can't learn about you or remember your preferences over time.

      Long-term memory

      Long-term memory takes the agent beyond a single conversation. It can remember your history, understand complex facts and build expertise from everything it has learned. Two capabilities make that possible:

      • Permanent storage. Unlike short-term memory, it doesn't reset. It's built on databases or , which also capture how pieces of information relate, and it can hold huge amounts of history.
      • Personalisation and history. A support agent with long-term memory remembers you had a specific problem three months ago. Instead of asking the same basic questions again, it tailors its answer to your history: faster, more personal, more helpful.

      The CoALA framework splits long-term memory into three types:

      Episodic memory

      lets an agent look back at its own history, like a person remembering a specific meeting or conversation rather than general facts. With it, the agent can do case-based reasoning: facing a new problem, it recalls a similar past situation, checks whether what it did then worked, and makes a better decision now. To do that, it keeps a structured log of each episode:

      For example, an AI financial advisor with episodic memory remembers your specific investment choices over several years. It doesn't just know the stock market in general; it knows your history, and recommends accordingly.

      Semantic memory

      is the agent's internal library of structured facts: definitions, formulas, rules. In simple terms, episodic memory lets an agent remember a specific conversation with you; semantic memory lets it know what the words in that conversation mean. Agents implement it with knowledge bases, symbolic AI or vector embeddings, which organise large amounts of data so the right fact can be found almost instantly. It's essential wherever domain expertise matters:

      • Medical tools: recalling symptoms and drug interactions
      • Business systems: company-wide policies and data
      • Legal assistants: searching thousands of past cases and precedents to give fact-based answers

      Semantic memory gives an agent a stable base of world knowledge, so it reasons from facts and rules instead of guessing from patterns.

      Procedural memory

      is the agent's ability to do: skills, workflows and action patterns such as how to use a tool, a reasoning strategy, or a step-by-step routine. It persists across sessions and improves with experience. Think of learning to ride a bike: at first you think about every step (balance, pedal, steer); later you just ride.

      iIn one line

      Semantic memory is what the agent knows, episodic memory is what it has experienced, and procedural memory is how it gets things done.

      3.3

      Why memory is hard

      Before building memory into an agent, know the six problems you're signing up for.

      1. 1

        Storage scalability

        As an agent talks to users and does tasks, the data it generates grows very quickly. Storing millions of high-dimensional embeddings (numeric representations of text) is expensive and heavy. You have to scale the store without it slowing down or costing a fortune.

      2. 2

        Memory refresh

        Real life changes. Agents need to update or overwrite old facts with new ones. Deciding what to keep, what to forget, and how to update outdated information without corrupting the rest is a delicate balance.

      3. 3

        Integration complexity

        Connecting an LLM to vector databases, external APIs and different memory layers (short-term vs long-term), and making them talk efficiently in real time, is a serious engineering job.

      4. 4

        Privacy and security

        Memory often holds personal or proprietary information, which makes it a target. If an agent remembers a card number or health data, that must be encrypted and tightly controlled. There's also risk: one user's memory leaking into another user's answers.

      5. 5

        Retrieval accuracy

        Stored memory is useless if the agent can't find the right piece. Searches often return noisy or only loosely related results. Improving is one of the biggest technical hurdles.

      6. 6

        Observability

        It's hard to see why an agent remembered one fact or failed to find another. Without tools to monitor, trace and visualise how memory is used, debugging and improving the agent is very difficult.

      An agent loop with memory

      Here is how an agent with both short-term and long-term memory handles one request, end to end.

      Step through

      Follow one request through memory

      Pick step 1. The example: a returning user asks a support agent "Has my replacement shipped yet?"
      1. 1

        Perceive the query

        From a user (text or voice), a system-triggered API event, or an automated change in the environment.

      2. 2

        Read short-term (working) memory

        Recent conversation history, current task progress, and the session's immediate state.

      3. 3

        Query long-term memory

        From vector databases or key-value stores: user preferences (settings and styles), historical data (past decisions and their outcomes), and a knowledge base (learned concepts, summaries, previous experiences).

      4. 4

        Reason

        Combine the input with retrieved short- and long-term context into one prompt, and let the LLM decide the best course of action.

      5. 5

        Act

        Produce a context-aware result: a personalised reply, a detailed plan, or a tool call.

      6. 6

        Save and learn

        Store new information (updated goals, success or failure signals, structured insights) back into memory for future tasks.

      3.5

      Memory building blocks on AWS

      AWS gives you a service for every kind of memory: fast stores for the conversation in progress, databases for facts, vector search for meaning, cheap storage for raw files, and glue to tie it together.

      With services for persistent storage, vector-based retrieval, workflow orchestration and session state, you can design agents that remember what matters, retrieve it when needed and act on it. The diagram below shows a typical memory architecture. At the centre, Amazon Bedrock or Amazon SageMaker AI provides the LLM, the agent's brain. Around it sit the memory stores and the orchestration layer that make the agent stateful.

      Each component, one at a time

      The agent's LLM

      It receives inputs, reasons through problems, and decides which memory to access or what action to take. On AWS this is typically a model accessed through Amazon Bedrock (Claude, Amazon Titan or Nova, Meta Llama and others), or an open-weight model such as Llama hosted on Amazon SageMaker AI. In this section's labs, the agent uses Claude Sonnet 4.6 (Notebook 1) and Claude Haiku 4.5 (Notebook 2) through Bedrock.

      Short-term memory (context)

      Stores the immediate history of the current interaction, for example the last 10 messages of a chat, so the agent knows what was just discussed and doesn't repeat itself. On AWS:

      • Amazon DynamoDB: a fast database for session state and recent chat transcripts.
      • Redis (Amazon ElastiCache or Amazon MemoryDB): an store for ultra-low-latency access to "hot" session data.
      • Amazon Bedrock AgentCore Memory: a managed, memory service that keeps track of the ongoing conversation for you. You'll use it in the second lab.

      Structured long-term memory

      Factual, relational data in traditional formats. If an agent needs a customer's recent order or a company's inventory, it looks here.

      • Amazon Aurora: a high-performance database for complex, structured relationships.
      • Amazon DynamoDB: for massive-scale metadata or historical records that don't need complex joins.
      • Amazon Neptune: a , for when the agent must understand relationships between entities. For example: "Which employees have worked on Project X and also know Python?"

      Semantic long-term memory (the RAG layer)

      Stores general knowledge, facts and concepts. It's arguably the most important layer for modern AI, and it powers , where relevant passages are searched for and handed to the model with the question. Data is stored as (lists of numbers that represent meaning), so the agent finds information by concept rather than exact keywords. Options on AWS:

      • Amazon OpenSearch Service: a search suite with vector-database capabilities to find relevant document chunks.
      • PostgreSQL with (for example on Amazon Aurora or Amazon RDS): a standard database with an extension that stores and searches embeddings.
      • Pinecone: a specialised third-party vector database built for high-speed semantic search.
      • Amazon Bedrock Knowledge Bases: a fully managed, serverless option for semantic memory inside Bedrock.

      Durable storage

      The where the original, raw source files live before they're processed or indexed into the other memory types. Amazon S3 is the foundation here: raw PDFs, text files, logs and images that the agent may need to reference or re-process later.

      Memory orchestration

      The logic layer, the connective tissue. It decides when to look in short-term memory and when to query semantic long-term memory.

      • AWS Lambda: serverless code that runs specific tasks, for example "fetch this user's profile from Aurora".
      • AWS Step Functions: a workflow orchestrator that stitches multiple tasks into a sequence.
      • Strands Agents SDK: the agent framework you've used since Section 1. It manages the conversation, tools and memory hooks so you write less plumbing.
      • LangGraph: a framework for building stateful, multi-step agents as a graph. It extends the LangChain ecosystem: instead of a simple linear chain, you design workflows as nodes and edges.

      That structure makes LangGraph well suited to complex, multi-turn agents that need planning, reflection or structured decisions. On AWS it can call models on Bedrock or SageMaker AI, keep its state in DynamoDB, Redis or AgentCore Memory, and be deployed on AWS Lambda, containers (Amazon ECS or Amazon EKS), or Amazon Bedrock AgentCore Runtime.

      3.6

      Lab: a personalised agent with Mem0

      Now we build it. A personal assistant that remembers each user's preferences, recalls them when relevant, and uses live web search, while keeping every user's memory private.

      The agent combines an LLM with persistent memory and an external tool. We use the Strands Agents SDK for orchestration, Claude on Amazon Bedrock as the LLM, as the persistent memory layer, and a web search tool for real-time information. Together they give each user tailored answers while keeping their memory isolated and secure.

      ✦Think of it like this

      A tailoring shop where every customer has their own measurement card in a locked drawer. When Mona walks in, the tailor is handed only Mona's drawer key. However nicely someone asks "just peek at Bunny's measurements", the key in the tailor's hand doesn't open Bunny's drawer. That's exactly how this lab keeps users apart.

      1. 1

        Agent initialisation

        Strands creates a separate, isolated agent for each user, so Mona's agent never sees Bunny's data.

      2. 2

        User interaction

        Users (Mona Mona and Bunny Kaushik in our example) send requests.

      3. 3

        Contextual retrieval (Mem0)

        The agent queries Mem0 for that user's preference memory: past interactions, private preferences and history.

      4. 4

        Reasoning (Amazon Bedrock)

        The query, the retrieved memories and the system prompt go to Claude on Bedrock.

      5. 5

        Tool use (web search)

        If the answer needs real-time information, the agent calls the web search tool (powered by DuckDuckGo).

      6. 6

        Final output

        The agent combines everything into a personalised answer for that user.

      The building blocks

      Strands Agents SDK, the orchestrator

      The model-driven framework that creates and runs each agent. It carries the system prompt that sets the rules: how to be personal, which tools to use, and how to treat other people's information.

      DuckDuckGo search, the web tool

      Fetches live information from the web through the ddgs library, so answers are up to date. No API key needed.

      Amazon Bedrock, the brain

      Claude Sonnet 4.6 runs the agent. Mem0 makes its own smaller Bedrock calls: Claude Haiku 4.5 to pull facts out of what users say, and Titan Text Embeddings v2 to turn those facts into vectors.

      Mem0, the memory

      An open-source memory layer for agents. It stores, organises and retrieves important information over time through simple SDK calls, and works across languages and frameworks. Other options with richer context handling exist, such as AgentCore Memory, which you'll meet in 3.8.

      What Mem0 does when the agent says "remember this"

      Mem0 doesn't just save the sentence. It runs a small pipeline that turns chatty text into clean, searchable facts:

      The agent drives all of this through one tool, mem0_memory, by choosing an action:

      ActionWhat it doesNeeds
      storeSave new information (Mem0 extracts the facts)content
      retrieveSemantic search for memories related to a queryquery
      listList all memories for the bound usernothing
      getFetch one memory by its IDmemory_id
      deleteDelete one memorymemory_id
      historySee how one memory changed over timememory_id
      iNotice what's missing

      There is no user_id in that list. The model picks the action and its content, query or memory ID; it never gets to say whose memories. That's decided in code, and it's the heart of this lab.

      A small compatibility fix

      Mem0 asks a Bedrock model to pull facts out of what the user says. The Mem0 release that strands-agents-tools supports sends both temperature and topP on every call, but current Claude models (4.5 and newer) accept only one of the two and reject the request. The patch below drops topP before the request leaves Mem0.

      cell 4: Mem0 + Claude shim
      import mem0.llms.aws_bedrock as mem0_bedrock

_original_init_client = mem0_bedrock.AWSBedrockLLM._initialize_aws_client


def _init_client_without_top_p(self):
    _original_init_client(self)
    original_converse = self.client.converse

    def converse(**kwargs):
        config = kwargs.get("inferenceConfig", {})
        if "temperature" in config:
            config.pop("topP", None)
        return original_converse(**kwargs)

    self.client.converse = converse


mem0_bedrock.AWSBedrockLLM._initialize_aws_client = _init_client_without_top_p
print("Mem0 Bedrock shim installed")
      ?What's a shim?

      A is a thin piece of code slipped between two parts that don't quite fit, like a wedge under a wobbly table leg. Here it wraps Mem0's Bedrock client so each request loses topP when temperature is present. Real projects hit version gaps like this all the time; a small, documented shim is the usual fix until the library catches up.

      Step 2: Define a system prompt

      The system prompt sets the agent's role, its limits, and how to use memory. In this use case it's critical that each agent works only with its own user's preferences.

      Step 3: A web search tool and one agent per user

      cell 6
      @tool
def websearch(keywords: str, region: str = "in-en", max_results: int = 5) -> str:
    """Search the web for up-to-date information.

    Args:
        keywords: The search query keywords.
        region: The search region, for example in-en, us-en, uk-en, wt-wt.
        max_results: The maximum number of results to return.
    """
    try:
        results = DDGS().text(keywords, region=region, max_results=max_results)
        return str(results) if results else "No results found."
    except Exception as e:
        return f"Exception: {e}"


def to_user_id(user_name: str) -> str:
    """Mem0 user IDs allow letters, digits, _ - . only."""
    return re.sub(r"[^A-Za-z0-9_\-.]", "_", user_name.strip().lower())


def create_agent(user_name: str) -> Agent:
    # The memory tool is bound to ONE user here, in code — not by the model.
    memory = Mem0MemoryTool(user_id=to_user_id(user_name))
    memory_tool = PythonAgentTool("mem0_memory", MEM0_TOOL_SPEC, memory.mem0_memory)
    return Agent(
        model=model,
        system_prompt=SYSTEM_PROMPT.format(user_name=user_name),
        tools=[memory_tool, websearch],
    )
      1. a

        websearch

        A Strands @tool that runs a DuckDuckGo text search. The default region in-en favours Indian English results. The docstring and Args become the tool description the model reads.

      2. b

        to_user_id

        Turns a display name into a safe ID: "Mona Mona" becomes mona_mona. Mem0 IDs may only contain letters, digits, _, - and ..

      3. c

        Mem0MemoryTool(user_id=...)

        Creates a memory tool that is bound to one user. Every store, search and list call it makes uses that user ID, and get, delete and history first check that the memory belongs to that user.

      4. d

        PythonAgentTool(...)

        Wraps the bound function with Mem0's standard tool description, so the agent sees an ordinary mem0_memory tool, but one that can only ever reach that user's memories.

      5. e

        Agent(...)

        A fresh Strands agent for this user, with the personalised system prompt and two tools: memory and web search.

        3.7

        Context management and memory optimisation

        Remembering everything is easy. Choosing what to put in front of the model, right now, is the real skill.

        Effective agent memory stands on three pillars: context management, retrieval strategies and memory optimisation. Context management means deciding what stays in the model's immediate context window (its working memory) and what is offloaded to external storage.

        Like a busy executive, an agent can get overwhelmed. Dump 1,000 pages into its context window and it suffers from : it becomes less focused, misses details and makes mistakes. So the principle is simple: treat context as a finite, precious resource. Smarter models need less hand-holding, but they still do their best work in a curated, environment.

        ✦Think of it like this

        An exam where you're allowed one A4 cheat sheet. Photocopy the whole textbook onto it in tiny print and you'll never find the formula you need. Write only the ten formulas this paper actually tests, and you're fast and accurate. The context window is that one sheet.

        The process of choosing what goes into the window is called :

        Effective agents succeed not by knowing everything, but by selecting the right context at the right time. For developers, optimising the window rests on three design pillars:

        System prompts

        Strike a balance: specific enough to guide the agent reliably, not so rigid that the system becomes .

        Tools

        -efficient, self-contained, and minimally overlapping, so the agent can choose between them without confusion.

        Examples (few-shot)

        A small set of diverse, representative examples, not a long laundry list of edge cases.

        When a task won't fit in one window

        Some jobs are too big for a single context window, for example migrating a large codebase. Four techniques help:

        1. 1

          Sliding window

          The most common, basic form: keep only a fixed window of the most recent tokens or messages. If the window holds 10 messages, message 11 deletes message 1, message 12 deletes message 2, and so on. The active memory slides forward, always keeping the N most recent interactions.

        2. 2

          Compaction

          Summarise the conversation so far and restart with a fresh context window holding only the critical decisions and the recent state.

        3. 3

          Structured note-taking

          The agent writes to a persistent external file (such as NOTES.md, or a memory tool) to track progress across sessions.

        4. 4

          Sub-agent architectures

          A lead agent coordinates several specialised sub-agents. Each does the heavy lifting in its own context and returns only a concise summary. You'll build multi-agent systems in the next section.

        iCompaction vs note-taking

        Compaction summarises the story of the conversation. Note-taking tracks the state of the project: "I've completed step 4, step 5 is pending, and the variable name is X."

        StrategyImplementationBest for
        Structured note-takingWrites facts to a fileComplex, multi-hour tasks (coding, research)
        Sliding windowDeletes the oldest dataShort-term, fast chats
        SummarisationCompactionStaying coherent over long horizons
        Graph-basedStructured metadata and indexingProviding high-signal identifiers
        Agentic RAG context through tools

        A sophisticated agent often uses both: a sliding window (or compaction) keeps the immediate conversation fluid and fast, while structured notes make sure critical facts, like a bug it found an hour ago, aren't accidentally pushed out by the sliding window.

        Memory optimisation

        The context window is a hard limit on how much text a model can process at once. Memory optimisation makes sure the agent gets the most valuable information without overflowing that window or running up huge costs. Done well, it makes an agent behave less like a forgetful goldfish and more like a thoughtful long-term companion, balancing what to keep, what to summarise and what to forget. Some strategies, like sliding window and compaction, serve both context management and memory optimisation.

        1. 1

          Sequential (keep it all)

          Every message is fed back to the LLM. Simple, but quickly hits token limits and increases cost.

        2. 2

          Sliding window

          Only the last N messages are kept. Fast and relevant, but forgets crucial details from earlier in the chat.

        3. 3

          Summarisation / compaction

          Periodically condense history into a short summary. Preserves the gist over long periods, but can lose specific minor details.

        4. 4

          Retrieval-based (RAG)

          History lives in an external store such as a vector database. The agent searches it and retrieves only the past facts relevant to the current question. That's exactly what Mem0 did in the lab.

          Advanced approaches

          Many agents start with these simple techniques, but advanced applications need more. Memory must do more than store old conversations: it must organise information, reduce redundancy, surface what matters most, and scale across long-running interactions. That has led to more sophisticated designs:

          Memory-augmented transformers

          Dedicated memory tokens or scratchpad spaces inside the model to retain key information.

          Hierarchical memory

          Layers organised by immediacy and importance, like a desk, a filing cabinet and an archive.

          Compression and consolidation

          Reduce raw text into embeddings, summaries or clusters of related memories.

          Graph-based memory networks

          Connect memories through entities and relationships, not just a timeline (remember the Neptune example).

          Strategic forgetting

          Remove low-value information on purpose while preserving the most useful knowledge.

          If you're building…Start with
          A simple chat appSliding window
          A fact-heavy appRetrieval-based (RAG) memory
          A complex, long-running appHierarchical or graph-based memory
          A production systemA hybrid: a sliding window for the immediate flow, plus retrieval for long-term facts

          How it's built

          Mem0 was a great way to see persistent memory in action: easy to plug in, and clear about how preferences get stored and retrieved.           ✦Think of it like this

          A hospital stay. While you're on the ward, nurses write everything on the bedside chart: every reading, every dose (short-term memory, raw events).           1. 1

            Raw events go to short-term memory

            During an interaction the agent produces raw events: user messages, tool calls, intermediate actions, system responses. They're written to short-term memory, the agent's temporary working area, which keeps continuity within the active session, like human working memory.

          2. 2

            The extraction module decides what's worth keeping

            Instead of copying everything into permanent storage, it reviews the raw events and picks out meaningful signals (preferences, goals, important facts, summaries of what happened) and turns them into structured memory records. This keeps long-term memory from filling up with low-value detail.

          3. 3

            Records are stored in long-term memory

            Long-term memory is a vector store, so the agent can later retrieve memories by meaning and relevance, not exact keywords. Over time this becomes a growing body of knowledge that improves personalisation and keeps decisions consistent across sessions.

          This tackles one of the biggest challenges in agentic AI: state management. Without memory, every interaction is independent. With this design, the agent captures fine-grained activity as events, keeps recent interactions in short-term memory, and its runtime behaviour stays in line with what it has stored.

          Short-term memory: actors, sessions and events

          Short-term memory preserves the immediate conversation, tracks active interactions, and keeps different users and sessions apart. It's organised around three concepts that answer three questions: who is interacting, what happened, and which conversation it belongs to.

          1. 1

            Actor: whose memory is it?

            Every event belongs to an : a specific user, or a user–agent combination. This keeps one user's conversation out of another's context, preventing cross-contamination.

          2. 2

            Events, grouped into a session

            During the interaction the agent creates : chat messages, or other data as JSON blobs. A represents one conversation or interaction period, so several messages are treated as one ongoing exchange.

          3. 3

            Synced into short-term memory

            Short-term memory holds three things: chat messages (the conversation history), session state (temporary variables, workflow progress) and checkpoints (snapshots that let a conversation be resumed). The two-way "sync" arrows mean the agent writes new information in and reads stored context back, so it can continue smoothly, remember what just happened, and recover if interrupted.

          iIn one line

          Events capture what happened, actors say who it belongs to, sessions say which conversation it was part of, and short-term memory holds the active working context that keeps the agent stateful and coherent.

          </>You'll see these exact names in Lab 2

          The LangGraph checkpointer maps thread_id to an AgentCore session ID and actor_id to an AgentCore actor ID. It stores each checkpoint as events in short-term memory.

          Long-term memory: strategies and namespaces

          Short-term memory explains how the agent tracks what's happening now. But agents also need to remember facts, preferences and outcomes over much longer periods. AgentCore Memory provides a structured way to extract useful information from ongoing interactions and store it as long-term memory. Two ideas drive it:

          • Memory strategies decide what is worth remembering and how to process it.
          • Namespaces decide where it's filed, so it can be found in the right context later.

          Together they move you beyond storing raw conversations to a memory that is selective, structured and searchable.

          Namespaces

          A namespace partitions memory, a bit like folders. You might keep one namespace for user preferences, another for past project details, another for general facts, so the agent never confuses different kinds of information. Their real power is that they let you zoom in or zoom out:

          LevelHoldsExample
          Global /Universal knowledge every agent must follow, regardless of the userCompany-wide compliance rules or security protocols
          StrategyDomain expertise, shared across many users but limited to one topicA medical agent's anatomy facts
          ActorUser preferences and recurring behaviour, so the agent remembers who you are and how you like to work"User84 prefers WhatsApp updates"
          SessionSummaries of specific conversationsTicket #456, so the agent knows what was said ten minutes ago versus ten months ago
          ?Namespaces are templates

          When you configure a strategy you give it a namespace template with placeholders, for example /users/{actorId}/preferences/ or /summaries/{actorId}/{sessionId}/. AgentCore fills in placeholders such as {actorId} and {sessionId} for each event, so every user's memories land in their own path automatically.

          Memory strategies

          When you create or update an AgentCore Memory, you define one or more strategies. They decide what is retained, how it's structured in namespaces, and how it's processed when events arrive. If no strategy is configured, no long-term memory is extracted; you get short-term memory only, which is exactly what Lab 2 uses. There are three types:

          Built-in

          Fully managed extraction for common needs. You pick one and AgentCore does the rest.

          Built-in with overrides

          Limited customisation of a built-in strategy: change its prompt instructions or the Bedrock model it uses, while keeping the managed pipeline and output format.

          Self-managed

          Full control over extraction and memory management. You run your own logic and write the resulting records yourself.

          Built-in strategyWhat it keepsLinks back to

          SemanticFacts and knowledge mentioned in conversationsSemantic memory (3.2)

          iMix and match

          A single memory resource can use built-in and custom strategies at the same time.

          The memory extraction module

          This module turns raw short-term events into useful long-term memory. Based on the selected strategy, it runs : it extracts important details, merges them with existing knowledge, and indexes the results for semantic search.

          1. 0

            Capture, then wait for the trigger

            Raw events are captured continuously in short-term memory. Instead of storing everything immediately, the extraction module runs in the background when the strategy's trigger fires: after a batch of new messages, or after a short pause in the conversation. New long-term records typically appear within tens of seconds, so don't expect them the instant a message is sent.

          2. 1

            Extraction

            Identifies and pulls meaningful information out of the raw interaction stream.

          3. 2

            Consolidation

            Merges it with existing knowledge. The module retrieves similar memories and then adds new information, updates an existing entry, or skips it if it's not meaningful or is redundant. An outdated memory isn't silently overwritten; it's marked invalid. The summary strategy has only a consolidation step, because a session summary is already structured content.

          4. 3

            Embedding and indexing

            The consolidated memory is converted to embeddings and indexed in long-term vector storage, ready for semantic search.

          The result: memory formation that is structured, not duplicated, and efficient, balancing real-time capture with durable, searchable long-term memory.
